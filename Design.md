# Quarkus Messaging Outbox: Design and Implementation

Nov 14, 2026 · @Ozan Gunalp

## Summary

A Quarkiverse extension, `quarkus-messaging-outbox`, adds an `OutboxEmitter<T>` that stores outgoing messages in the caller's database transaction and relays them to the channel's connector until the broker acknowledges them. Version 1 targets Quarkus 4.0 and SmallRye Reactive Messaging 5.0, and needs no change in either.

The proposal answers [smallrye-reactive-messaging#3599](https://github.com/smallrye/smallrye-reactive-messaging/issues/3599). All names, config keys and defaults below are proposals.

### Goals

- **Atomicity:** no message for a rolled-back transaction, and no lost message for a committed one.
- **At-least-once delivery** to any connector, using the connector's ack as the delivery signal.
- **Declarative use:** one injection point and per-channel configuration, with no outbox code in the application.
- **Low happy-path latency:** the relay is woken right after commit, and polling is only the recovery path.
- **Safe with several application instances** sharing one database.
- **Hibernate ORM store first, Hibernate Reactive store second**, behind a store SPI.

### Non-goals

- Exactly-once delivery. Consumers deduplicate on the outbox id header. The future work section lists the ways to add it later.
- An inbox or consumer-side deduplication feature.
- A change-data-capture relay. The write side stays usable with Debezium when the relay is disabled.
- Support for runtimes other than Quarkus in version 1.
- A plain JDBC store in version 1.

## Target platform

The extension targets Quarkus 4.0 and SmallRye Reactive Messaging 5.0, with Java 21 as the minimum. It cannot be backported to Quarkus 3 as designed, because the emitter factory method that receives the channel configuration exists only in 5.0.

On 14 November 2026 the latest tags were Quarkus 4.0.0.CR1 and SmallRye Reactive Messaging 5.0.0-RC2. Quarkus `main` builds against 5.0.0-RC2, Hibernate ORM 8.0.0.Beta4, Hibernate Reactive 5.1.0.Beta1, Vert.x 5.2.3 and Mutiny 3.3.1. The source checks in this document were made on those branches.

## Background

The issue asks for a declarative outbox so that messages survive broker downtime. The reporter uses AMQP, and today writes to an outbox table in a `@Transactional` method and drains it with a cron job.

The design reuses extension points that already exist. I checked each one in the `main` branch of both repositories on 14 November 2026.

| Extension point | Where | What the outbox uses it for |
| --- | --- | --- |
| `EmitterType` marker, `@EmitterFactoryFor`, `EmitterFactory` | SmallRye, `api` module | Registers `OutboxEmitter` as a custom emitter type, as `KafkaTransactions` does |
| `EmitterFactory.createEmitter(configuration, defaultBufferSize, channelConfig)` | SmallRye, `api` module | Gives the factory the channel `Config`, so outbox settings need no new API |
| `MessagePublisherProvider` | SmallRye, `api` module | The emitter implementation exposes the relay as the channel's publisher |
| `OutgoingInterceptor.beforeMessageSend`, which returns a `Message` | SmallRye, `api` module | Maps portable outbox metadata to connector metadata |
| `WiringProcessor.extractComponents` collects every bean with `@EmitterFactoryFor` | Quarkus, messaging deployment module | A factory from a third-party extension is wired without core changes. `ConnectorAttachmentCustomEmitterTest` covers this path |

### Gaps found in the same check

| Gap | Effect | Handling in version 1 |
| --- | --- | --- |
| `EmitterConfiguration` exposes name, emitter type, overflow settings and broadcast, but not the payload type | The relay cannot know which type to deserialize to | The extension captures the type from the injection point at build time |
| Kafka serializer auto-detection in `SmallRyeReactiveMessagingKafkaProcessor` recognises a fixed list of emitter types | No default `value.serializer` for an `OutboxEmitter` channel | Documented requirement at first, then a build step in the extension |
| Dev UI lists only the built-in emitter types | Outbox channels are not shown | The extension ships its own card |

### Prior art

- **`KafkaTransactions` and `PulsarTransactions`** are custom emitters with a different send contract. They set the precedent for a dedicated emitter type.
- **Kafka checkpoint state stores** in Quarkus select a Hibernate ORM or Hibernate Reactive implementation by identifier. The store SPI follows that shape.
- **The Debezium outbox extension** covers the write side only and relies on change data capture for the relay.

## User-facing API

Applications inject `OutboxEmitter<T>` on a normal outgoing channel. The channel keeps its connector configuration, and the emitter decides when messages reach it.

```java
@ApplicationScoped
public class CustomerService {

    @Inject
    @Channel("customer-events")
    OutboxEmitter<CustomerCreated> events;

    @Transactional
    public void create(Customer customer) {
        customer.persist();
        events.sendAndAwait(new CustomerCreated(customer.id));
    }
}
```

```java
@Experimental("Outbox emitter")
public interface OutboxEmitter<T> extends EmitterType {

    Uni<Void> send(T payload);

    Uni<Void> send(String key, T payload);

    <M extends Message<? extends T>> Uni<Void> sendMessage(M message);

    void sendAndAwait(T payload);

    void sendAndAwait(String key, T payload);

    <M extends Message<? extends T>> void sendMessageAndAwait(M message);
}
```

### Send contract

- **Completion means stored, not delivered.** The returned `Uni` completes when the record is written in the current transaction. Broker delivery happens later. In fallback mode it completes on the broker ack, or on the fallback write when the direct send fails.
- **The message's own ack is called once the record is stored.** A nack is called only if the store write fails.
- **Blocking stores run on the caller thread.** With the Hibernate ORM store, `send` does the write when subscribed, on the subscribing thread. `sendAndAwait` is the natural form in `@Transactional` code.
- **No transaction is an error by default.** `require-transaction=false` lets the store write in its own transaction.

### Message key

The key names the entity whose records must stay in order, usually the aggregate id. It drives `ordering=key` and is passed to the broker as its ordering key. It is resolved in this order:

The key is a `String` in version 1. This was decided on 14 November 2026. Two consequences follow:

- **Extractors must return a `String`.** Any other type fails the `send` with a clear error, and is not converted silently with `toString()`.
- **Kafka channels need a string key serializer.** The Kafka bridge passes the key as a `String` record key.

1. **Explicit key.** The `key` argument of `send(key, payload)`, or `OutboxMetadata.withKey(...)` on a message.
2. **`KeyValueExtractor`.** The extractor selected for the channel, described below.
3. **No key.** Under `ordering=key` such records are unordered, and the relay logs one warning per channel.

Key extraction reuses SmallRye's existing `KeyValueExtractor` from the `io.smallrye.reactive.messaging.keyed` package, the interface behind `KeyedMulti`. Its contract takes a `Message`, so it applies to outgoing messages unchanged, and an application can share one extractor between its consuming and producing sides.

- **Call:** the write side calls `extractKey(message, String.class)` and stores the result in `msg_key`.
- **Payload:** it stores the result of `extractValue(message, payloadType)`, so a wrapper payload that holds key and value is split.
- **Selection:** `outbox.key-extractor` names the extractor bean class. When it is unset, the highest-priority extractor whose `canExtract` accepts the channel's first message is used for that channel, as for `KeyedMulti`.
- **`@Keyed` is not usable here yet.** It targets method parameters only, so it cannot sit on an emitter injection point.
- **Shipped extractors:** the Kafka bridge adds one that reads the key from `OutgoingKafkaRecordMetadata`. The extractors shipped by the Kafka and Pulsar connectors read incoming metadata and never match an outgoing message.

```java
@ApplicationScoped
public class CustomerEventKeyExtractor implements KeyValueExtractor {

    @Override
    public boolean canExtract(Message<?> first, Type keyType, Type valueType) {
        return first.getPayload() instanceof CustomerEvent;
    }

    @Override
    public Object extractKey(Message<?> message, Type keyType) {
        return ((CustomerEvent) message.getPayload()).customerId();
    }

    @Override
    public Object extractValue(Message<?> message, Type valueType) {
        return message.getPayload();
    }
}
```

The outbox key should also be the broker's ordering key. The relay only guarantees the order in which records reach the broker, and the connector bridges pass the same key on as the Kafka record key or the AMQP group id.

### Delivery modes

| Mode | Behaviour | Guarantee |
| --- | --- | --- |
| `transactional` (default) | Always store in the caller's transaction, wake the relay after commit | At-least-once, atomic with the business data |
| `fallback` | Send directly, and store only when the send is nacked or times out | Survives broker outages. A crash between the send and the fallback write can lose the message |

### Channel configuration

Keys sit under `mp.messaging.outgoing.<channel>.outbox.`.

| Key | Default | Meaning |
| --- | --- | --- |
| `store` | the only store present | `hibernate-orm` or `hibernate-reactive` |
| `persistence-unit` | default unit | Persistence unit that owns the outbox table |
| `mode` | `transactional` | `transactional` or `fallback` |
| `require-transaction` | `true` | Fail `send` when no transaction is active |
| `relay.enabled` | `true` | Set to `false` when another process drains the table |
| `ordering` | `strict` | `strict`, `key` or `none` |
| `max-in-flight` | `1024` | Upper bound on unacknowledged records for `key` and `none` |
| `poll-interval` | `5s` | Recovery poll period |
| `batch-size` | `100` | Records claimed per query |
| `lease-duration` | `30s` | How long a claim or a channel lease stays valid without renewal |
| `backoff.initial` | `1s` | First retry delay, doubled per attempt with jitter |
| `backoff.max` | `1m` | Retry delay ceiling |
| `max-attempts` | `-1` | Attempts before a record is parked. `-1` retries forever |
| `retention` | `delete` | `delete` on delivery, or `keep` and mark as sent |
| `retention.period` | `7d` | Age at which kept records are purged |
| `fallback.timeout` | `5s` | Wait for the broker ack in `fallback` mode |
| key-extractor | by priority | Class name of the KeyValueExtractor bean used to resolve the message key |

## Architecture

The emitter has two halves that meet only in the database: a write side that runs in the caller's transaction, and a relay that is the publisher of the outgoing channel.

&#91;embedded content: write path and relay path · 7 components\]

The top row runs inside the business transaction. The bottom row runs later, in the relay, and repeats until the connector acknowledges the record.

### Write side

1. `send` asks the `OutboxRecordMapper` to turn the message into an `OutboxRecord`.
2. `OutboxStore.persist` writes the record through the caller's session, in the caller's transaction.
3. The store registers an after-commit callback that signals the relay for that channel.
4. The message's ack is called and `send` completes. Nothing has gone downstream.

If the transaction rolls back, the row is never visible and the callback does not fire.

### Relay

One relay runs per outbox channel. It is a `Multi` exposed through `MessagePublisherProvider`, so the connector subscribes to it like any emitter.

1. The relay wakes on a commit signal or on the poll timer. Signals that arrive while it is busy are coalesced.
2. It claims up to `min(downstream demand, batch-size)` pending records, oldest first.
3. It maps each record back to a `Message` whose ack and nack functions call the store.
4. On ack, the record is deleted or marked as sent. On nack, its attempt count and next attempt time are updated.
5. It loops while the last claim was full, then waits for the next signal or tick.

The commit signal only triggers a normal claim query. There is one path to the broker, so immediate dispatch and recovery polling cannot send the same record twice, and ordering rules apply to both.

### Record lifecycle

| State | Meaning | Leaves the state when |
| --- | --- | --- |
| `PENDING` | Stored and waiting. May carry a next attempt time after a nack | A relay claims it |
| claimed | `PENDING` with a live `claimed_until` lease held by one relay | Ack, release, or lease expiry. A nack ends the claim only on unordered channels. On ordered channels the record stays claimed while it waits for its retry |
| `SENT` | Acknowledged, kept only when `retention=keep` | The purge job removes it after `retention.period` |
| `FAILED` | Parked after `max-attempts` or a non-retryable mapping error | An operator resets or deletes it |

### Threading

- **Hibernate ORM store:** claim, ack and nack writes run on a worker thread, each in its own short transaction.
- **Hibernate Reactive store:** the same operations run on a duplicated Vert.x context owned by the relay.
- **Emission** follows the usual emitter rules, so connectors see no difference from a standard emitter.

## Data model and store SPI

All channels share one table, `outbox_record`, plus a small `outbox_lease` table used for ordered channels.

### `outbox_record`

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | UUID, primary key | Outbox id, sent as a header for consumer deduplication |
| `seq` | bigint from a sequence | Claim order |
| `channel` | varchar | Outgoing channel name |
| `msg_key` | varchar, nullable | Ordering and partitioning key |
| `payload` | blob | Serialized payload |
| `payload_type` | varchar | Java type name used to deserialize |
| `headers` | text (JSON) | Portable headers, including trace context |
| `status` | smallint | `PENDING`, `SENT` or `FAILED` |
| `attempts` | int | Delivery attempts so far |
| `next_attempt_at` | timestamp | Earliest time of the next attempt |
| `claimed_by` | varchar, nullable | Relay instance id holding the claim |
| `claimed_until` | timestamp, nullable | Claim lease expiry |
| `created_at` | timestamp | Used for lag metrics and retention |
| `last_error` | varchar, nullable | Last nack reason, truncated |

One index covers the claim query: `(channel, status, next_attempt_at, seq)`.

`outbox_lease` has `channel` (primary key), `owner` and `expires_at`. It elects the single active relay for a channel whose ordering is `strict` or `key`.

### Claim query

```sql
select * from outbox_record
 where channel = :channel
   and status = 0
   and next_attempt_at <= :now
   and (claimed_until is null or claimed_until < :now)
 order by seq
 fetch first :n rows only
 for update skip locked
```

The store then sets `claimed_by` and `claimed_until` on the selected rows and commits. Hibernate renders the locking clause per dialect through its skip-locked lock mode, so the store carries no hand-written SQL per database.

The query above is the `ordering=none` form. Ordered channels use two variations, both driven by `ClaimRequest`:

- **No `next_attempt_at` filter.** A record waiting for a retry must not be skipped, or its successors would overtake it. The relay honours the next attempt time itself.
- **`msg_key not in (:excludedKeys)`** for `ordering=key`, so that a blocked key does not fill the relay's buffer.

### SPI

```java
public interface OutboxStore {

    /** Writes the record in the caller's transaction and signals the relay after commit. */
    Uni<Void> persist(OutboxRecord record);

    /** Claims deliverable records, oldest first, under a lease. */
    Uni<List<OutboxRecord>> claim(ClaimRequest request);

    Uni<Void> delivered(OutboxRecord record);

    /** Records a failed attempt. The record stays claimed in ordered modes. */
    Uni<Void> retry(OutboxRecord record, Instant nextAttempt, Throwable failure);

    Uni<Void> park(OutboxRecord record, Throwable failure);

    /** Gives claimed records back, on shutdown or when a key's queue is trimmed. */
    Uni<Void> release(List<OutboxRecord> records);

    /** Acquires or renews the channel lease. Always true for unordered channels. */
    Uni<Boolean> holdLease(Duration lease);

    Uni<OutboxStats> stats();

    Uni<Integer> purge(Instant sentBefore);

    interface Factory {
        OutboxStore create(OutboxStoreContext context);
    }
}

public record ClaimRequest(
        int max,
        Duration lease,
        boolean dueOnly,          // true for ordering=none, false for strict and key
        Set<String> excludedKeys  // keys blocked by a failing record, for ordering=key
) {}
```

On an ordered channel, every relay write (`claim`, `delivered`, `retry`, `park`, `release`) fails with `LeaseLostException` when the store no longer holds the channel lease. The store checks this in the same transaction as the write, using an `epoch` column on `outbox_lease` that is incremented at each acquisition. The relay stops on that exception.

`OutboxStoreContext` carries the channel name, the channel `Config`, the relay instance id and the commit signal. Factories are CDI beans selected with `@Identifier`, like checkpoint state stores.

### Hibernate ORM store

- **`persist`** uses the `Session` of the configured persistence unit, so the insert is flushed and committed with the business entities.
- **Transaction check:** it reads the JTA status and fails when none is active, unless `require-transaction=false`.
- **Commit signal:** it registers an interposed synchronization on the `TransactionSynchronizationRegistry` and signals on `STATUS_COMMITTED`.
- **Relay operations** use a `StatelessSession` in a new transaction, so claimed entities never build up in a persistence context.

### Hibernate Reactive store

- **`persist`** must use the reactive session already bound to the caller's Vert.x context. A separate connection would commit on its own and break atomicity.
- **Commit signal:** there is no JTA synchronization. The reactive transactions extension in Quarkus 4 has a completion hook, but it accepts a single resource and also runs after a rollback, so the store cannot use it yet. Until a reliable hook is found, the store signals after `persist` with a short delay, and the poll timer covers the rest.
- **Relay operations** open their own session and transaction on the relay's context.

### Schema management

The extension contributes the entity to the persistence unit, so `drop-and-create` and `update` strategies create the table. Applications that use Flyway, Liquibase or `validate` must add the tables themselves. The documentation ships DDL for PostgreSQL, MariaDB, MySQL, SQL Server and Oracle.

## Serialization and metadata mapping

The record stores a serialized payload plus a small portable envelope, and the relay rebuilds a typed message from it. Connector-specific metadata objects are never stored.

```java
public interface OutboxRecordMapper {

    OutboxRecord toRecord(String channel, Message<?> message);

    Message<?> toMessage(OutboxRecord record, Type payloadType);
}
```

### Default mapper

- **Payload:** JSON through the application's Jackson `ObjectMapper`. `byte[]` and `String` payloads pass through unchanged.
- **Payload type:** the type argument of the `OutboxEmitter<T>` injection point, captured at build time and registered for reflection in native mode.
- **Envelope:** an optional `OutboxMetadata` on the message supplies string headers, and the key is resolved as described under Message key. Nothing else from the message metadata is stored.
- **Relay side:** the rebuilt message carries `OutboxMetadata` with the outbox id, key, headers and attempt number.

Applications replace the mapper by providing their own bean, for example to store Avro bytes.

### Connector bridges

A bridge is an `OutgoingInterceptor` that translates `OutboxMetadata` into the connector's outgoing metadata in `beforeMessageSend`. Bridges are optional beans, enabled only when the connector is present.

| Connector | Key maps to | Headers map to | Outbox id maps to |
| --- | --- | --- | --- |
| AMQP 1.0 | Group id, when `ordering=key` | Application properties | Message id |
| Kafka | Record key | Record headers | `outbox-id` header |
| Others | Not mapped in version 1 | Not mapped in version 1 | Available from `OutboxMetadata` |

A connector without a bridge still delivers payloads. Applications can add their own interceptor for it.

### Tracing

The mapper writes the current trace context into the headers at `send`. The relay restores it before emitting, so the connector's span links back to the business request and not to the poll loop.

### Compatibility of stored records

Records written by one application version may be relayed by the next. Payload classes must therefore stay backward-readable across a deployment, as they already must for consumers. A record that cannot be deserialized is parked as `FAILED` at once, with the error stored, and does not block the channel.

## Delivery semantics

In `transactional` mode every committed record is delivered at least once, and no record of a rolled-back transaction is ever delivered. Duplicates are possible and carry the same outbox id.

### Ordering

| `ordering` | Relay behaviour | Active relays per channel | Order kept |
| --- | --- | --- | --- |
| `strict` (default) | One record in flight. A nack stops the line and retries that record | One, elected through `outbox_lease` | By `seq`, across the channel |
| `key` | One record in flight per key, keys in parallel up to `max-in-flight`. Records without a key are unordered | One, elected through `outbox_lease` | By `seq`, per key |
| `none` | Up to `max-in-flight` records in flight | All instances compete with skip-locked claims | None |

Two limits apply to every ordered mode:

- **`seq` is assigned at insert, not at commit.** Two overlapping transactions can commit in the opposite order of their `seq` values, and the relay may send the later one first. Order is guaranteed within a transaction and between transactions that do not overlap.
- **`strict` costs throughput.** Each record waits for the previous ack. Channels that need volume should use `key` or `none`.

### How the relay keeps order

Version 1 ships all three modes. This was decided on 14 November 2026.

On an ordered channel the relay holds the channel lease, so its in-memory state is the only dispatch state for that channel.

1. **Claim in `seq` order.** The relay claims the oldest unclaimed records, whether or not a retry is due.
2. **Queue per key.** Each claimed record goes to the FIFO queue of its key. `strict` uses a single queue for the whole channel. Records without a key bypass the queues under `key`.
3. **One in flight per queue.** The relay emits the head of a queue and waits for its ack before emitting the next.
4. **Retry in place.** On a nack the head stays claimed and stays at the head. The relay stores the attempt with `retry`, waits until the next attempt time, and emits it again.
5. **Bounded buffer.** The relay stops claiming when it holds `max-in-flight` records, counting queued and in-flight ones. `strict` stops at `batch-size`.
6. **Blocked keys under `key`.** While a key's head is waiting for a retry, the relay releases that key's queued tail and adds the key to `excludedKeys`. The key is claimed again once its head is acked or parked.
7. **Takeover.** A relay that takes over the lease claims by `seq` again. A head record whose next attempt time is in the future is held until that time.

Under `none` there are no queues. A nack releases the record with its next attempt time, and any relay claims it again when due.

### Retries

- A nack schedules the record at `now + min(backoff.max, backoff.initial x 2^attempts)` with jitter.
- In `strict` and `key` modes the failing record keeps its place, and the records behind it in the same queue wait. Nothing overtakes it.
- After `max-attempts` the record is parked as `FAILED` and its queue moves on. The default `-1` never parks, which suits `strict`.

### Several instances

- **Unordered channels** scale out: each instance claims disjoint batches.
- **Ordered channels** run one relay at a time. Other instances retry the lease every `lease-duration / 3` and take over when it expires.
- **Claims are leases.** A live relay renews claims that are still in flight. Claims of a dead instance expire after `lease-duration`, and another relay picks the records up.

### Shutdown

The relay stops claiming, waits for in-flight acks up to the application's shutdown timeout, releases what is left and gives up its channel lease. Released records are picked up at once by another instance or on restart. This should plug into the framework-level graceful shutdown from SmallRye PR #3460 once it lands.

### Failure matrix

| Failure | Outcome |
| --- | --- |
| Business transaction rolls back after `send` | The row is never visible. Nothing is sent |
| Crash after commit, before the relay wakes | The poll timer of any instance finds the record |
| Broker unreachable | Records are nacked or time out, then retried with backoff. Lag shows in health and metrics |
| Crash after the broker ack, before the delete | The record is sent again. Same outbox id |
| Relay instance dies with claimed records | Claims expire after `lease-duration`. Another relay sends them |
| Connector never acks or nacks | The claim expires and the record is sent again. A duplicate is possible |
| Database unreachable | `send` fails and the business transaction fails with it. The relay pauses and retries its queries |
| Payload cannot be deserialized | The record is parked as `FAILED` at once |
| Two ordered relays after a long pause of the lease holder | The stale holder's claim writes fail on its expired lease, and it stops. A duplicate is possible, a reorder is not once it stops |

### `fallback` mode

- `send` emits directly and waits for the ack up to `fallback.timeout`.
- On nack or timeout it stores the record in a new transaction, and the relay takes over.
- A crash between the failed send and the store write loses the message.
- A send that times out but later succeeds produces a duplicate.
- Ordering is always `none`, since stored records are sent after later direct sends.

How `fallback` mode is built:

- **Two sources, one publisher.** The emitter's publisher merges direct sends with the relay's stream. The connector sees a single upstream.
- **Direct path.** `send` emits the message and completes when the connector acks it.
- **Fallback path.** On a nack, or when no ack arrives within `fallback.timeout`, the emitter stores the record in a new transaction of its own. `send` completes when that write commits.
- **No downstream demand** counts as a timeout, so a stalled connector fills the table and not the heap.
- **Both paths fail.** If the fallback write also fails, `send` fails with the store error and carries the send error as suppressed.
- **Configuration check.** `mode=fallback` with `ordering` other than `none` fails at startup.

## Extension structure

### Emitter factory

```java
@EmitterFactoryFor(OutboxEmitter.class)
@ApplicationScoped
public class OutboxEmitterFactory implements EmitterFactory<OutboxEmitterImpl<Object>> {

    @Inject ChannelRegistry channelRegistry;
    @Inject @Any Instance<OutboxStore.Factory> storeFactories;
    @Inject OutboxRecordMapper mapper;
    @Inject OutboxChannelTypes payloadTypes;

    @Override
    public OutboxEmitterImpl<Object> createEmitter(EmitterConfiguration configuration, long defaultBufferSize) {
        return create(configuration, OutboxConfig.defaults());
    }

    @Override
    public MessagePublisherProvider<?> createEmitter(EmitterConfiguration configuration, long defaultBufferSize,
            Config channelConfig) {
        return create(configuration, OutboxConfig.from(channelConfig));
    }

    @Produces
    @Typed(OutboxEmitter.class)
    @Channel("") // stream name is ignored during type-safe resolution
    <T> OutboxEmitter<T> produce(InjectionPoint injectionPoint) {
        String channel = ChannelProducer.getChannelName(injectionPoint);
        return channelRegistry.getEmitter(channel, OutboxEmitter.class);
    }
}
```

`create` picks the store factory by identifier, builds the store and the relay, and returns an `OutboxEmitterImpl` whose `getPublisher()` is the relay.

## Observability

The signal that matters is the age of the oldest pending record per channel: it rises when the broker is down, when the relay is stuck, and when a `strict` channel is blocked by one record.

### Metrics

All meters carry a `channel` tag and are registered only when Micrometer is present.

| Meter | Type | Meaning |
| --- | --- | --- |
| `messaging.outbox.pending` | Gauge | Records in `PENDING` |
| `messaging.outbox.failed` | Gauge | Records in `FAILED` |
| `messaging.outbox.oldest.age` | Gauge, seconds | Age of the oldest pending record |
| `messaging.outbox.delivered` | Counter | Records acknowledged |
| `messaging.outbox.retries` | Counter | Nacks that led to a retry |
| `messaging.outbox.delivery.latency` | Timer | Time from `created_at` to ack |

Gauges read `OutboxStore.stats()` on a timer, not on every scrape.

### Health

- **Readiness** reports `DOWN` when the store cannot be queried.
- **Lag is reported as data, not as `DOWN`.** A broker outage should not take the application out of rotation, since accepting writes into the outbox is the point of the feature. An optional `health.max-age` turns sustained lag into `DOWN` for teams that want it.

### Logs and Dev UI

- One warning when a record is first nacked, one when it is parked, and a rate-limited warning while a `strict` channel is blocked.
- The Dev UI card lists pending and failed counts per channel, with actions to retry or delete parked records.

## Future work: effectively-once delivery

Version 1 delivers at-least-once with a stable outbox id, which is what the transactional outbox pattern promises. Avoiding duplicates is possible later, per broker or on the consumer side, and nothing in this design blocks it.

### Why at-least-once is the correct baseline

The [pattern's reference description](https://microservices.io/patterns/data/transactional-outbox) guarantees that a message is sent if and only if the transaction commits. It lists duplicate publication by the relay as a known issue, and asks consumers to be idempotent. An outbox that never loses a committed message, never sends a rolled-back one, and sends a stable id is a complete implementation.

The duplicate has one cause: the broker accepts a record, and the relay crashes or loses the ack before it deletes the row. Removing it needs either an atomic broker write and row delete, or someone who recognises the second copy.

### Options

| Option | Who removes the duplicate | Applies to | Effort |
| --- | --- | --- | --- |
| Broker duplicate detection | The broker, on the outbox id | Brokers with a publish-side deduplication feature | Small, in the connector bridge |
| Transactional relay | The relay, on recovery | Kafka | A Kafka-specific relay mode |
| Consumer inbox | The consumer, on the outbox id | Every broker | A companion feature for `@Incoming` methods |
| Debezium as the relay | Kafka Connect | Kafka | None in the extension, with `relay.enabled=false` |

### Broker duplicate detection

The bridge copies the outbox id into the broker's deduplication field. Only the Artemis row is checked against its documentation; the others are from memory and need verification.

| Broker | Mechanism | Limit |
| --- | --- | --- |
| Artemis | `_AMQ_DUPL_ID` message property ([docs](https://activemq.apache.org/artemis/docs/latest/duplicate-detection.html)) | Circular, fixed-size id cache per address. Use over AMQP 1.0 is untested |
| Pulsar | Broker deduplication on producer name and sequence id | Needs monotonic sequence ids from a single relay |
| Amazon SQS FIFO | Message deduplication id | Five-minute window |
| RabbitMQ classic queues, MQTT, Google Pub/Sub, SNS, SQS standard | None known on the publish side | The relay cannot prevent the duplicate |

Artemis is the first candidate, because it is the reporter's broker family and the change is one property in `AmqpOutboxBridge`.

### Transactional relay for Kafka

The idempotent producer removes duplicates only within one producer session, so it does not cover a relay restart. A transactional producer can:

1. The relay sends a batch inside a Kafka transaction.
2. In the same transaction it writes the batch's outbox ids to a progress topic.
3. On restart it reads the last committed marker and deletes those rows without resending.

Only the last batch is ever in doubt, so the marker stays small. The marker holds ids and not a `seq` watermark, because a lower `seq` can commit late. The `transactional.id` also fences a stale relay, which overlaps with the channel lease.

### Consumer inbox

The consumer stores each processed outbox id in its own database, in the same transaction as its business change, and skips ids it has already stored. This is the only option that works with every broker, and it also absorbs redeliveries caused by the broker. It could reuse the store machinery of this extension and wrap `@Incoming` methods.

### Debezium as the relay

Debezium reaches exactly-once into Kafka through Kafka Connect, which since Kafka 3.3 can write source records and their offsets in one Kafka transaction ([KIP-618](https://cwiki.apache.org/confluence/display/KAFKA/KIP-618:+Exactly-Once+Support+for+Source+Connectors)). [Debezium 3.3](https://debezium.io/releases/3.3) lists exactly-once delivery as enabled for all connectors. The guarantee relies on Kafka transactions, so it applies to Kafka only. Users who need it today can keep the outbox write side and disable the relay.

### Suggested order

1. Artemis duplicate id in the AMQP bridge, after a test over AMQP 1.0.
2. Consumer inbox as an optional companion.
3. Transactional relay for Kafka, if users ask for it and Debezium is not an option for them.

## Open questions and upstream follow-ups

### Open questions

- [ ] **Commit hook for Hibernate Reactive.** Quarkus 4 adds reactive @Transactional through quarkus-reactive-transactions (preview). Its ReactiveResource hook is injected as a single bean, which Hibernate Reactive already provides, and its afterCommit also runs after a rollback. Can it accept several resources and report the outcome? Without one, the reactive store depends on a delayed signal and the poll timer.
- [ ] **Config prefix.** Which keys does the `channelConfig` passed to `createEmitter` expose for an emitter channel? The 5.0 Javadoc says it is the outgoing channel configuration, and null without an outgoing connector. Milestone 0 confirms that outbox keys are readable from it and settles the null case.
- [ ] **Pipelined strict ordering.** With an idempotent Kafka producer, the relay could send a batch without waiting for each ack and still keep order. Is a connector-specific fast path worth the complexity?
- [ ] **Commit-order sequencing.** Should a later version offer commit-ordered claims, for example through a transaction id watermark on PostgreSQL, to close the overlapping-transaction gap?
- [ ] **One table or one per channel.** A shared table is simpler. Per-channel tables isolate noisy channels and simplify partitioning.
- [ ] **Default for `max-attempts` with `key` and `none`.** Retrying forever is right for `strict`. A finite default may be kinder for unordered channels.

* [ ] **Typed keys.** Version 1 keys are strings. Should a later version store serialized keys of any type, for Kafka channels with non-string key serializers?

### Upstream follow-ups

None blocks version 1. Each removes a workaround.

| Repository | Change | Removes |
| --- | --- | --- |

| Quarkus | A build item that lets extensions declare emitter types and their payload argument | The extension's own Kafka serializer default and Dev UI gap |
| SmallRye Reactive Messaging | Portable outgoing metadata for key and headers | Per-connector bridges |
| SmallRye Reactive Messaging | Relay and store SPI moved into a connector-agnostic module, once stable | The Quarkus-only limitation |
